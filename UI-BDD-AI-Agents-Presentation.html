The Foundation

Built on Playwright's own agent concept — made more advanced

Playwright already ships with three built-in agent roles that explore an app, write tests, and fix failures — all using the same MCP connection. This project keeps that core idea and turns it into a more specialized, four-agent pipeline built for BDD-style testing.

📓 Shared memory across runs
🔒 Session safety gate
🥒 Native BDD / Cucumber output
🎯 Deep-then-light exploration
🧩 Per-role isolation
Still the same MCP foundation underneath — just four specialized roles instead of three general ones2 / 7
The Cast

What each agent actually does

Four narrow specialists, not one do-everything assistant — each has one clear job, one clear trigger, and one clear output.

ui-test-planner
Runs once, at the start
Looks at the whole app once and writes down everything it finds — pages, buttons, filters. Becomes the shared notes every other agent relies on.
Gives it: the app
Gets back: shared notes file
ui-tc-generator
A new feature has no test case yet
Tries the new feature out live in the browser first, then writes a clear, well-structured test case for it.
Gives it: a rough description
Gets back: a proper test case
ui-feature-builder
A test case is ready
Builds the whole product in one pass — test script, page objects and working automation code. Explores each part of the live app once, and uses that single look for both the script and the code.
Gives it: a test case (file or name)
Gets back: script + code, ready to run
ui-test-healer
A test starts failing
Investigates as deeply as it needs to — no shortcuts — finds the real cause, applies the smallest fix, and confirms it actually works.
Gives it: a failing test
Gets back: a working test again
Each agent stays in its own lane — no overlap, no guesswork3 / 7

Under The Hood

How does an AI agent actually "see" the app?

Through something called MCP — think of it as a remote control that connects the agent to a real, running browser, so it can look at and interact with the actual app instead of guessing.

🤖
The Agent
Decides what to do next
sends a command
🔌
MCP
The remote-control link in between
controls a real browser
🖥️
The Real App
Actually opens, clicks, and reads back what's on screen
1

Open the page

The agent tells MCP to open a specific screen in the app — just like a person typing a web address.

2

Look around

MCP reads back exactly what's on screen — button names, labels, colors — as real, current information.

3

Interact

The agent can click, type, hover, or select — the same actions a real user would make.

4

Double-check

After acting, it looks again to confirm what actually happened — not what it expected to happen.

Why this matters: every label, button name, and behavior that ends up in the final test code was actually seen live — not guessed. That's what makes these tests trustworthy. (One quirk: this connection starts up quietly and can take 15–30 seconds with no visible output — that's normal, not frozen.)

MCP = the agent's eyes and hands on the real, running app5 / 7
Guardrails

What keeps this safe to run on its own

Four simple rules keep the agents reliable — plus one hard safety check before any of them ever touches a real browser.

📓

One shared memory

Everyone reads and writes the same notes file. A fix made in one place helps everywhere else, automatically.

🎯

Right amount of checking

One agent explores deeply, once. The next agent only needs a quick recheck — unless something actually changed.

⚡

Efficient by default

Agents read only what's relevant and ask the browser only what's needed — same thoroughness, far less waste.

🚧

No cross-wires

Different user types get their own separate test files, so similarly-worded steps never get mixed up.

🔒 Session safety check

Runs before any agent opens a browser. Without it, a logged-out session can make the browser hang forever, waiting on a login screen no one is watching.
1 · Check
Is the login still valid right now?
→
2 · Refresh, if needed
Agent logs back in by itself — no one has to do it manually
→
3 · Go, or stop safely
Proceeds only once confirmed — otherwise it stops and reports why
The same safety check runs every single time — never skipped, never assumed6 / 7
